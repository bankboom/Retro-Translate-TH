# มาตรฐานคำแปลและฟอนต์ไทย (Quality First)

## A. ความเที่ยงตรงของเนื้อหา
- ต้องเข้าใจผู้พูด ผู้รับสาร เหตุการณ์ ช่วงเวลา แนวเกม บุคลิก น้ำเสียง ก่อนตัดสินใจคำแปล เลือกสำนวนไทยเป็นธรรมชาติ ไม่แปลตรงตัวจนผิดความหมาย และไม่ใส่รายละเอียดที่ต้นฉบับไม่มี
- รักษาชื่อบุคคล สถานที่ ท่า อาชีพ ไอเทม สกิล ค่า ATK/DEF/HP ระดับ ตัวเลข หน่วย และคำสั่งเกม; ใช้ glossary ที่อนุมัติแล้ว; ความกำกวมส่ง `NEEDS_CONTEXT` ไม่เดา
- ตรวจสะกด การเว้นวรรค การใช้คำสุภาพ/สรรพนาม การสอดคล้องของตัวละคร และการตัดบรรทัด; ถ้าต้องย่อให้เหมาะ UI ต้องไม่สูญความหมายสำคัญ
- ห้ามแก้ placeholder (`%s`, `%d`, `{name}` ฯลฯ), escape sequence, byte tokens, tag, ตัวควบคุม และลำดับโดยไม่พิสูจน์ grammar จากเกม
- ทุกบรรทัดต้องมี Source ID และบริบทจริง (scene, speaker, quest, UI) เท่าที่หาได้; สถานะ `DRAFT` จนตรวจบริบทแล้วจึง `REVIEWED`

## B. ฟอนต์ไทย (ตรวจตาม renderer จริง)
- หา encoding, glyph index/atlas, text renderer, codepage, tile format, advance width, baseline, ascent/descent, bearing, kerning, line-height, clipping, textbox/line-break rules ก่อนฉีดข้อมูล
- วิเคราะห์คลัสเตอร์ตัวอักษรไทย: พยัญชนะ+สระบน (`ิ ี ึ ื`), สระล่าง (`ุ ู`), วรรณยุกต์ (`่ ้ ๊ ๋`), `็ ์` และ `ำ` รวมการจัดวาง/แยกส่วนตาม engine; อย่าสันนิษฐานว่า Unicode combining ทำงานเอง
- ทดสอบอย่างน้อย `กา มา ภาษา ปัญหา น้ำ สำ ต้ ตุ ตุ๊กตา ม้า ป่า ผู้ใหญ่ เก่ง ขึ้น รู้` และสตริงที่มีตัวเลข/ASCII/control codes; เลือกตัวอย่างจริงจากเกมเพิ่มเติม
- ตรวจทุกขนาดฟอนต์ที่เกมใช้จริงและทุกพื้นหลังหลัก (เมนู บทสนทนา ต่อสู้ กล่องชื่อ คำอธิบายไอเทม) รวมหลายความยาว; screenshot คู่ baseline/candidate ที่ scene และ scale เท่ากัน
- กฎความสวยงาม: ไม่มีสระ/วรรณยุกต์ตกขอบ ซ้อนพยัญชนะ ห่างผิดปกติ สูงผิดสัดส่วน บรรทัดทะลุ หรือ glyph สลับเป็นสัญลักษณ์; ระยะ `า` ต้องดูความสูง/สมดุลกับพยัญชนะ ไม่ใช่บังคับความสูงเชิงตัวเลขที่ผิดกับรูปแบบฟอนต์
- ถ้าดูด้วยไฟล์ไบนารีอย่างเดียว: G3 = PENDING; หากภาพยังอ่านไม่ออกหรือสมส่วนไม่ดี: FAIL; ห้ามปรับ glyph ทั้ง atlas จากหนึ่งตัวอย่างโดยไม่ regression test

## C. มาตรฐานอนุมัติ
- G2 = PASS เฉพาะเมื่อ coverage ตามขอบเขต, context review, spelling, glossary, tokens, numeric semantics และข้อจำกัดความยาวผ่านพร้อมหลักฐาน
- G3 = PASS เมื่อมีภาพจริงจาก emulator พร้อม build ID/scene/font size และไม่มี defect ที่ทำให้เข้าใจผิด/อ่านลำบาก; การตัดสินความงามต้องใช้ผู้ตรวจมนุษย์เมื่อเป็นไปได้
- G4 ต้องทดสอบบูต เส้นทางเกมที่เกี่ยวข้อง เซฟ/โหลด ไม่ใช่แค่ ROM checksum
- ระบุความคืบหน้า 5 ตัวแยกกัน: discovered / drafted / reviewed / injected / on-screen-verified; ตัวหารและ scope ต้องตรงกัน

## D. ตรวจความถูกต้องตามบริบทตลอด 6 เฟส

กำหนดการตรวจ **Meaning, Context, Thai grammar/style, Terminology, Continuity, Technical tokens/width** ก่อนเลื่อนคำแปลแต่ละรายการเป็น `REVIEWED`. Phase 1 ตรวจเฉพาะแถวทดลอง, Phase 2 ตรวจเสียงและความเหมาะสมในฉาก Emulator, Phase 3/4/5 ตรวจทุกแถวที่จะนับเข้า reviewed coverage 50/70/100% ของ scope ที่ยืนยันแล้ว, Phase 6 ตรวจทวนการเล่นจริงและ regression. ผู้ตรวจต้องแยกสมมติฐานเรื่องฉาก/ผู้พูดออกจากหลักฐาน. หากยังไม่แน่ใจให้ `NEEDS_CONTEXT` แม้สำนวนจะอ่านสวย. ดู `docs/SIX_PHASE_CONTEXT_QA_TH.md` สำหรับเกณฑ์นับผลและข้อยกเว้น ASCII smoke test.
